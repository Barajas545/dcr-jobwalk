# Platform research (2026-11-02)

Facts the app codes against, from primary sources (specs, MDN, WebKit/Chromium, vendor docs). Each area is researched, then re-checked by a skeptical second pass; the heading says which state it is in. H/M/L = confidence.

## Device orientation, compass and motion — verified by a second pass

- **[H] CONFIRMED. W3C DeviceOrientation angles are intrinsic Tait-Bryan Z-X'-Y''. The device frame is x to the right, y toward the top of the screen and z out of the screen, in the natural orientation, and it does not change when the screen rotates. Ranges: alpha [0,360), beta [-180,180), gamma [-90,90). Precision is capped at 0.1 deg (acceleration 0.1 m/s^2, rotation rate 0.1 deg/s). Events fire only when the document is 'visible' and only in secure contexts. The spec recommends a change threshold of at most 1 degree.** TR status re-checked: 'W3C Candidate Recommendation Draft', dated 26 October 2026 (the Editor's Draft carries the same date). Editors are Reilly Grant (Google) and Marcos Caceres (Apple). Rotations are right-handed. Chromium actually fires on a change of 0.1 deg or more (kOrientationThreshold = 0.1); see the Chromium firing fact. (https://www.w3.org/TR/orientation-event/ ; https://w3c.github.io/deviceorientation/ ; https://raw.githubusercontent.com/w3c/deviceorientation/main/index.bs)
- **[H] CONFIRMED. The spec rotation matrix (Appendix A.2 getRotationMatrix) is R = Rz(alpha)·Rx(beta)·Ry(gamma). Its columns are the device x, y and z axes in the Earth frame (x=East, y=North, z=Up).** m11=cZ·cY−sZ·sX·sY, m12=−cX·sZ, m13=cY·sZ·sX+cZ·sY; m21=cY·sZ+cZ·sX·sY, m22=cZ·cX, m23=sZ·sY−cZ·cY·sX; m31=−cX·sY, m32=sX, m33=cX·cY (X=beta, Y=gamma, Z=alpha). I compared this numerically against an explicit Rz·Rx·Ry product over 20,000 random poses: max error 2e-16. Row 3 (m31,m32,m33) is world-Up expressed in device coordinates, which the 'how the phone is held' fact relies on. (https://raw.githubusercontent.com/w3c/deviceorientation/main/index.bs (lines ~860-915) ; own numeric script)
- **[H] CONFIRMED, with one caveat added. Spec compassHeading() (A.1) is the azimuth of v=[0,0,−1], the back-camera direction: Vx=−m13, Vy=−m23. It is mathematically identical to atan2(Vx,Vy) taken clockwise from north. The spec function returns NaN when the phone is flat. atan2 does not return NaN there, but the value it returns is meaningless: atan2(−0,−0)=180°. A pitch guard is still required.** Vx=−cZ·sY−sZ·sX·cY; Vy=−sZ·sY+cZ·sX·cY. Over 20,000 random non-degenerate poses, atan2 and the spec code agree to 1e-13 deg. Spec checks: gamma=0 gives −alpha; beta=90 gives −(alpha+gamma). The spec says these formulas assume absolute angles. (https://w3c.github.io/deviceorientation/ (Appendix A.1) ; own numeric script)
- **[H] CONFIRMED. Back-camera pitch is asin(−m33) = asin(−cos(beta)·cos(gamma)). It is 0 when the phone is upright, −90 when the phone is flat face-up, and positive when the phone is tilted back past vertical. The portrait top-edge (+Y) heading is atan2(m12,m22), which equals −alpha exactly for any gamma whenever |beta|<90.** Numeric checks: (0,90,0) gives 0°; (0,60,0) gives −30°; (0,120,0) gives +30°; (0,0,0) gives −90°. Across 20,000 random poses with |beta|<89, top-edge heading equals −alpha to within 1e-13. The difference between the camera heading and the top-edge heading is atan(tan γ / sin β). It is LARGEST when the phone is near flat (27° at β=20,γ=10; 64° at β=5,γ=10) and about γ when the phone is upright (10.2° at β=80,γ=10). The ~75° switch-over to the image-up heading is an engineering choice, not from the spec. (https://w3c.github.io/deviceorientation/ ; own numeric script)
- **[H] CONFIRMED. Absolute orientation is referenced to MAGNETIC north on every platform, so the app must add declination itself. The spec likens absolute orientation to Android TYPE_ROTATION_VECTOR and Core Motion xMagneticNorthZVertical. Chromium Android maps absolute orientation to TYPE_ROTATION_VECTOR, falling back to accelerometer+magnetometer fusion. Android TYPE_HEADING (true north, accuracy at 68%) exists natively, but Chromium's PlatformSensorProvider.java has no mapping for it. Chromium platform_sensor_provider_android.cc ABSOLUTE_ORIENTATION_EULER_ANGLES fallback: (A) quaternion from TYPE_ROTATION_VECTOR, (C) accelerometer+magnetometer. I found no declination step in this code path. Orientation Sensor spec: 'y-axis ... points towards magnetic north'. (https://w3c.github.io/deviceorientation/ ; https://developer.android.com/reference/android/hardware/SensorEvent ; https://raw.githubusercontent.com/chromium/chromium/main/services/device/generic_sensor/platform_sensor_provider_android.cc ; https://raw.githubusercontent.com/chromium/chromium/main/services/device/generic_sensor/android/java/src/org/chromium/device/sensors/PlatformSensorProvider.java ; https://w3c.github.io/orientation-sensor/)

- **[M] CORRECTED rationale. To get an absolute back-camera heading on iOS: learn offset = wrap(alphaRel − (360 − webkitCompassHeading)) while the top edge is near horizontal, then alphaAbs = alphaRel − offset, run the W3C matrix, and add declination. The right reason to gate on small |beta| is different from the original. With the phone flat-ish, the top edge is horizontal, so its azimuth is well-conditioned and matches Apple's documented semantics. Near upright, the top edge points at the sky, its azimuth is ill-conditioned, and iOS behaviour is undocumented.** The original wording ('the camera-vs-top-edge difference is already 14° at beta=45') mixed up two separate things. That difference is atan(tan γ / sin β): it grows toward FLAT and is about γ near upright. It is the reason NOT to use webkitCompassHeading directly as the camera heading, because they differ by 27° at β=20,γ=10 and by about γ when upright. It is not the reason for where to learn. A yaw offset is a pre-multiplied Rz, so it shifts alpha exactly for any beta/gamma, gimbal-lock poses included. I checked offset recovery numerically for offsets of 0, 37 and −120°. Gate on accuracy 0..~25 (not −1), smooth with a circular EMA, re-learn every time the phone is lowered, and discard the offset on any visibility change (see the WebKit visibility fact). **Recommendations**

- Data safety: save every photo or video sample with its RAW inputs: alpha, beta, gamma, source ('abs' / 'ios' / 'relative' / 'manual'), webkitCompassHeading and webkitCompassAccuracy, the iOS offset in use, screen.orientation.angle, the gravity holdAngle, the declination value and model ('WMM2025'), and the timestamp of the pose sample (last.t) next to the shutter time. Then any later fix to the maths or calibration can recompute headings without losing data. When the user drags a photo's arrow to correct it, keep the original value alongside the correction.
- Compute the camera heading as atan2(−m13, −m23) and the pitch as asin(−cos β·cos γ). atan2 avoids NaN, but when the phone is flat it returns an arbitrary 180°, so keep the |pitch| > ~75° switch to the image-up heading.
- Never sniff iOS with `typeof DeviceOrientationEvent.requestPermission === 'function'`, because Chrome 151+ has it too. Branch on the presence of 'ondeviceorientationabsolute' in window (Android) and on a numeric e.webkitCompassHeading (iOS). On iOS, e.absolute is undefined, not false.
- Call DeviceOrientationEvent.requestPermission() and DeviceMotionEvent.requestPermission() with no argument, synchronously inside the 'Start walk' tap, before any await. Neither engine implements the spec's absolute argument. On iOS, a call with no gesture REJECTS with NotAllowedError while the state is 'prompt', so wrap launch-time calls in try/catch and show the button. Assume iOS may ask again on each launch.
- Treat an event with alpha === null, from either event, as 'no compass, or sensors blocked'. Show a visible prompt and fall back to manual heading. Never silently drop these events.
- On Chrome, keep the last orientation value. Events fire only when an angle changes by 0.1° or more, so a phone held still emits nothing. Use the cached pose at the shutter and store its age.
- On iOS, validate webkitCompassHeading on webkitCompassAccuracy >= 0. WebKit reports a heading of 0 with accuracy −1 when no heading exists. Learn the alpha offset only while the top edge is near horizontal, re-learn it whenever the phone is lowered, and DISCARD it on visibilitychange or pageshow, because WebKit restarts Core Motion and the arbitrary yaw re-bases. Do not use webkitCompassHeading directly as the camera heading: when the phone is flat-ish it differs from the camera direction by atan(tan γ / sin β), and near upright its behaviour is undocumented.
- For photo up and roll and for the plan's image-up arrow, use the gravity-based holdAngle = atan2(m31, m32), snapped to 90°, rather than screen.orientation.angle. The screen angle stays 0 under iPhone rotation lock, reads 90 in portrait on iPad (WebKit treats landscape as natural there), and may be collapsed to 0/90 in privacy modes.
- Take photos in-page with getUserMedia, so the exact pose is sampled at the moment of the in-page shutter tap. With <input capture> the shutter moment is unknown and sensor events stop while the page is hidden. If you keep it as a fallback, flag the pose as approximate and reset the iOS offset afterwards.
- Never use DeviceMotionEvent.interval: iOS reports about 0.0167 (seconds) and Chrome reports 16 (ms). Compute dt from event.timeStamp. For gyro yaw, use rotationRate.gamma (about the screen normal), or project onto world-Up with R. rotationRate.alpha is the rate about device X.
- Add WMM2025 declination yourself on both platforms, because both report magnetic north. If you vendor geomagnetism 0.2.0, know that it hard-stops on 13 Nov 2029 unless allowOutOfBoundsModel is set. Convert its JSON to a JS module, keep the Apache-2.0 LICENSE, precache it, and check it against the NCEI WMM2025 test values. magvar 2.2.0 (MIT) is an alternative with an explicit east-positive sign and a Date or decimal-year argument; both packages are CommonJS and need porting.
- Job sites are full of steel, and the WMM omits local anomalies that can exceed 10°. Show the heading accuracy (iOS only), warn when the accuracy is −1 or large, and let the user drag-correct the arrow while keeping the original.
- Treat browser PDR as a short-range aid only. Use |accelerationIncludingGravity| so the sign does not matter, calibrate K over a known plan distance (fixed K gives about 20% error, adaptive about 5% in the literature), and re-anchor often with GPS or a tap on the plan.

Verify: (a) whether webkitCompassHeading follows the top edge or the camera when upright; (b) whether iOS alpha jumps after an app switch; (c) the sign of iOS accelerationIncludingGravity.z when face-up; (d) whether the permission persists across Home Screen launches; (e) screen.orientation.angle with rotation lock on; (f) on iPad, screen.orientation.angle vs window.orientation in portrait.

**Pose from W3C alpha/beta/gamma (absolute): back-camera heading/pitch, gravity-based hold angle, image-up heading (numerically verified)**

```js
const D2R = Math.PI / 180, R2D = 180 / Math.PI;
const norm360 = d => ((d % 360) + 360) % 360;
// R = Rz(alpha)·Rx(beta)·Ry(gamma) (W3C App. A); Earth x=East, y=North(MAGNETIC), z=Up
export function cameraPose(alpha, beta, gamma) {
  const cX = Math.cos(beta*D2R),  sX = Math.sin(beta*D2R);
  const cY = Math.cos(gamma*D2R), sY = Math.sin(gamma*D2R);
  const cZ = Math.cos(alpha*D2R), sZ = Math.sin(alpha*D2R);
  const m11 = cZ*cY - sZ*sX*sY, m12 = -cX*sZ, m13 = cY*sZ*sX + cZ*sY;
  const m21 = cY*sZ + cZ*sX*sY, m22 = cZ*cX,  m23 = sZ*sY - cZ*cY*sX;
  const m31 = -cX*sY,           m32 = sX,     m33 = cX*cY;
  const pitch = Math.asin(Math.max(-1, Math.min(1, -m33))) * R2D;  // +up, -90 = floor
  const camHeading = norm360(Math.atan2(-m13, -m23) * R2D);         // == spec compassHeading(); meaningless near |pitch| 90
  // how the phone is HELD (CCW from portrait; 0/90/180/270 like screen.orientation.angle) from gravity:
  const holdAngle = norm360(Math.atan2(m31, m32) * R2D);            // immune to rotation lock / iPad natural-landscape
  const holdOK = Math.hypot(m31, m32) > 0.5;                          // false when phone near flat
  const t = (Math.round(holdAngle / 90) % 4) * 90 * D2R, ux = Math.sin(t), uy = Math.cos(t);
  const upHeading = norm360(Math.atan2(m11*ux + m12*uy, m21*ux + m22*uy) * R2D);
  const planHeading = Math.abs(pitch) < 75 ? camHeading : upHeading;  // 75 = engineering choice
  return { camHeading, pitch, holdAngle, holdOK, upHeading, planHeading };
}
// checks: (0,90,0)->cam 0,pitch 0,hold 0; (30,90,20)->cam 310; (0,60,0)->pitch -30; (90,0,-90)->cam 0,hold 90
```

**iOS: learn alpha offset from webkitCompassHeading (validate on accuracy, reset on visibility change)**

```js
const wrap180 = d => ((d % 360) + 540) % 360 - 180;
let iosOffset = null;                         // alphaRel - alphaAbs (deg)
addEventListener('visibilitychange', () => { iosOffset = null; });   // WebKit stops/restarts Core Motion -> yaw re-bases
addEventListener('pageshow', () => { iosOffset = null; });
function onIOS(e) {
  const h = e.webkitCompassHeading, acc = e.webkitCompassAccuracy;   // WebKit gives h=0, acc=-1 when no heading
  // top-edge heading == 360 - alphaAbs exactly (any gamma, |beta|<90); learn only while top edge is near horizontal
  if (acc >= 0 && acc <= 25 && Math.abs(e.beta) < 35 && Math.abs(e.gamma) < 35) {
    const s = wrap180(e.alpha - (360 - h));
    iosOffset = iosOffset == null ? s : wrap180(iosOffset + 0.1 * wrap180(s - iosOffset));
  }
  const raw = [e.alpha, e.beta, e.gamma, h, acc];
  if (iosOffset == null) return onNoCompass('ios-learning', raw);  // 'hold the phone flatter for a moment'
  const alphaAbs = ((e.alpha - iosOffset) % 360 + 360) % 360;      // magnetic
  setLast(cameraPose(alphaAbs, e.beta, e.gamma), raw, 'ios');
}
```

**Step detector (heuristic thresholds); dt from timeStamp, never event.interval (iOS reports seconds)**

```js
const G = 9.80665; let lp = G, phase = 'wait', peak = -Infinity, valley = Infinity, lastStepT = 0;
let K = 0.47; // Weinberg constant, calibrate per user over a known plan distance
addEventListener('devicemotion', e => {
  const a = e.accelerationIncludingGravity; if (!a || a.x == null) return;
  const m = Math.hypot(a.x, a.y, a.z);       // magnitude: immune to iOS/Android sign difference
  lp += 0.24 * (m - lp);                      // ~3 Hz one-pole low-pass at 60 Hz
  const t = e.timeStamp;                      // ms; e.interval is 16 on Chrome but ~0.0167 on iOS
  if (phase === 'wait' && lp > G + 1.2) { phase = 'peak'; peak = lp; }
  else if (phase === 'peak') { peak = Math.max(peak, lp); if (lp < G) { phase = 'valley'; valley = lp; } }
  else if (phase === 'valley') {
    valley = Math.min(valley, lp);
    if (lp > G) {
      const dt = t - lastStepT;
      if (valley < G - 0.8 && dt > 300 && dt < 2000) onStep(K * Math.pow(peak - valley, 0.25));
      if (valley < G - 0.8) lastStepT = t;
      phase = 'wait'; peak = -Infinity; valley = Infinity;
    }
  }
});
// gyro yaw rate between fixes: rotationRate.gamma (about screen normal), NOT rotationRate.alpha (that is about device X)
```

**Recommendations**

- Open ONE long-lived rear stream per walk. Use facingMode {ideal:'environment'} and LANDSCAPE numbers (width {ideal:4032}, height {ideal:3024}); bug 323550 shows portrait numbers give sideways output on iOS 26.6/27 (front camera confirmed, rear untested). Read the real size after the first frame (the 'loadeddata' or 'resize' event, or a drawn frame), not from getSettings() right after getUserMedia. Never call getUserMedia for a different camera while recording: on iOS it ENDS the old track, and a track-set change stops MediaRecorder.
- Sample position, heading, pitch, altitude, accuracy and timestamp synchronously at the shutter tap, BEFORE any await. takePhoto can take hundreds of ms, reconfigure the camera, or pause the preview (Chrome closes the preview session; WebKit may switch format and mute/unmute).
- takePhoto: call getPhotoCapabilities() and pass BOTH imageWidth and imageHeight inside its ranges. Chrome rejects out-of-range values, and with none it uses the first JPEG size. On WebKit those ranges are VIDEO ranges, and a size that maps to another preset switches the camera format for the shot (mute/unmute, possible torch flicker). Keep the stream at the size you will request, and set a photoInFlight flag so your mute handler ignores the expected mute. Validate every result (decodes, area not below the video frame, not black). Retry once, then fall back to grabFrame (Chrome; Safari 26+) or drawImage(video) on a canvas of at most 16,777,216 px (iOS 17 limit; 67,108,864 px on iOS 18+).
- Data safety for photos: write the Blob and its metadata in ONE IndexedDB transaction, and show 'saved' only in oncomplete. Never rely on EXIF GPS: takePhoto writes none, iOS file-input capture strips it, and Android redacts location by default. Write EXIF yourself from stored metadata if exports need it. Request navigator.storage.persist() and show the result in diagnostics.
- Video type selection: use only explicit codec strings, in this order: 'video/mp4;codecs=avc1.640028,mp4a.40.2', 'video/mp4;codecs=avc1.42E01F,mp4a.40.2', 'video/mp4;codecs=avc1,mp4a.40.2', 'video/webm;codecs=vp9,opus', 'video/webm;codecs=vp8,opus'. Do NOT use bare 'video/mp4' (Chrome may write VP9-in-MP4) and never 'h264' or 'aac' (WebKit rejects them). Set videoBitsPerSecond explicitly (Chrome 2.5 Mbps default, WebKit 10 Mbps). Store rec.mimeType as read in onstart or the first dataavailable, not the requested string.
- Chunk durability: ALWAYS use a timeslice. In Chrome, start() without one keeps the whole WebM in memory until stop(). Call start(1000), put each non-empty chunk to IndexedDB under [recId, seq], and serialize all writes on one promise chain so the 'complete' header cannot land before the last chunk. Write a 'recording' header before start(). On launch, rebuild unfinished recordings from chunk 0 with no seq gaps, check playback with a hidden <video>, and label them 'recovered, may be truncated'. Delete chunks only after the joined Blob is stored and verified.
- Interruptions: on visibilitychange to hidden, pagehide, track 'ended', or a 'mute' that is not from your own takePhoto, call rec.stop() (it flushes a final dataavailable). Avoid real navigations while recording, since WebKit discards the recording on back-forward-cache suspension. After returning, re-acquire the camera if the track ended or stayed muted, and start a NEW MediaRecorder. Do not use speechSynthesis during capture on iOS (reported to mute getUserMedia). Detect frozen frames (no 'resize' or frame-callback progress) on Android, where Camera2 disconnects silently.
- Duration: store your own measured durationMs and the timed path; never trust video.duration on MediaRecorder output (fMP4 has 0, chunked WebM has none). Remux on export if a server is ever added.
- Lens on iOS: enumerateDevices shows Triple, Dual Wide, Ultra Wide and the plain 'Back Camera' separately (labels localized). Offer 'Lock lens', which selects the device whose getCapabilities().zoom is missing or has min >= 1, and store deviceId plus label. Record the zoom level and the deviceId with every photo. On Android, ultra-wide is reachable only if the phone exposes it as its own 'camera N, facing back'.
- Torch and zoom: feature-detect with getCapabilities() after the stream is live. Use applyConstraints({advanced:[{torch|zoom}]}), keep torch state in your own variable (stale before iOS 18.4), and re-apply after any reconfiguration.
- Wake lock: call navigator.wakeLock.request('screen') FIRST in the 'Start walk' tap handler, before any await such as getUserMedia, so WebKit still sees the user gesture. Re-request on visibilitychange to visible, catch NotAllowedError, and show a 'screen may sleep' badge. iOS Home Screen mode before 18.4 has no wake lock.
- Native camera fallback (<input capture>): before opening it, persist the walk state and the sensor sample to IndexedDB. Android can kill Chrome while the camera app is in front, so the photo is lost and the page reloads. Stop or pause your own getUserMedia stream first. Warn that the native path adds no location on iOS.
- Expect a camera permission prompt on every cold launch of the iOS Home Screen app (bug 327237, open). Request the camera only from a user tap inside the walk, never at page load.
- Ship a diagnostics screen for each device (iOS 17/18/26/27, two or three Android phones) that logs: every isTypeSupported candidate and the resulting rec.mimeType, track capabilities and settings before and after the first frame, getPhotoCapabilities, the actual takePhoto JPEG size and whether mute fired, the torch/zoom ranges, storage.persisted(), and a truncated-chunk playback test.

**Photo: sample sensors first, takePhoto inside ranges, verified fallback**

```js
let photoInFlight = false; // WebKit may mute/unmute the track during takePhoto: expected, not an interruption
async function capturePhoto(track, videoEl, sampleSensors) {
  const meta = sampleSensors();                    // synchronous, BEFORE any await
  if (track.readyState !== 'live' || !track.enabled) throw new Error('camera not live'); // Chrome rejects otherwise
  photoInFlight = true;
  try {
    if ('ImageCapture' in window) {
      const ic = new ImageCapture(track);
      for (let attempt = 0; attempt < 2; attempt++) {
        try {
          const pc = await ic.getPhotoCapabilities();
          // Chrome: must be within pc ranges (else 'imageWidth setting out of range'); max -> largest JPEG size.
          // WebKit: pc = VIDEO ranges; a size != current preset reconfigures the camera for this shot.
          const blob = await ic.takePhoto({ imageWidth: pc.imageWidth.max, imageHeight: pc.imageHeight.max });
          if (await looksValid(blob, videoEl)) return { blob, meta, source: 'takePhoto' };
        } catch (e) { /* WebKit readiness/first-photo bugs (fixed 2026-05 on main) -> retry once */ }
      }
    }
    const w = videoEl.videoWidth, h = videoEl.videoHeight;
    const s = Math.min(1, Math.sqrt(16777216 / (w * h)));   // iOS 17 canvas area cap
    const c = document.createElement('canvas');
    c.width = Math.floor(w * s); c.height = Math.floor(h * s);
    c.getContext('2d').drawImage(videoEl, 0, 0, c.width, c.height);
    const blob = await new Promise((res, rej) => c.toBlob(b => b ? res(b) : rej(new Error('toBlob null')), 'image/jpeg', 0.92));
    c.width = c.height = 0;
    return { blob, meta, source: 'canvas' };
  } finally { photoInFlight = false; }
}
async function looksValid(blob, videoEl) {
  const bmp = await createImageBitmap(blob);
  const bigEnough = bmp.width * bmp.height >= 0.9 * videoEl.videoWidth * videoEl.videoHeight;
  const c = document.createElement('canvas'); c.width = c.height = 8;
  const g = c.getContext('2d'); g.drawImage(bmp, 0, 0, 8, 8); bmp.close();
  const d = g.getImageData(0, 0, 8, 8).data; let sum = 0;
  for (let i = 0; i < d.length; i += 4) sum += d[i] + d[i + 1] + d[i + 2];
  return bigEnough && sum / (64 * 3) > 4;         // reject all-black first photo
}
// then: ONE IndexedDB transaction { blob, meta, source }, show 'saved' only on tx.oncomplete
```

**MediaRecorder: explicit codecs, timeslice, serialized crash-safe writes**

```js
const CANDIDATES = [
  'video/mp4;codecs=avc1.640028,mp4a.40.2', // H.264 High + AAC
  'video/mp4;codecs=avc1.42E01F,mp4a.40.2', // H.264 Baseline + AAC
  'video/mp4;codecs=avc1,mp4a.40.2',
  'video/webm;codecs=vp9,opus',             // Chrome; iOS 18.4+ if VP9 setting on
  'video/webm;codecs=vp8,opus'
]; // NOT bare 'video/mp4' (Chrome may pick VP9-in-MP4); NOT 'h264'/'aac' (WebKit rejects)
const mimeType = CANDIDATES.find(t => MediaRecorder.isTypeSupported(t)) || '';

function startRecording(stream, recId, db, isPhotoInFlight) {
  const opts = { videoBitsPerSecond: 6_000_000 }; if (mimeType) opts.mimeType = mimeType;
  const rec = new MediaRecorder(stream, opts);
  let seq = 0, t0 = 0, chain = Promise.resolve();
  const enqueue = fn => (chain = chain.then(fn, fn));          // keep IDB writes in order
  enqueue(() => putHeader(db, { recId, state: 'recording', startedAt: Date.now(), requested: mimeType }));
  rec.onstart = () => { t0 = performance.now(); const actual = rec.mimeType; enqueue(() => patchHeader(db, recId, { mimeType: actual })); };
  rec.ondataavailable = e => { if (e.data && e.data.size) { const s = seq++; enqueue(() => putChunk(db, recId, s, e.data)); } };
  rec.onerror = e => enqueue(() => patchHeader(db, recId, { error: String(e.error || e.type) }));
  rec.onstop = () => { const durationMs = performance.now() - t0; enqueue(() => patchHeader(db, recId, { state: 'complete', durationMs, chunks: seq })); };
  rec.start(1000);                                              // ALWAYS a timeslice (Chrome buffers all in memory otherwise)
  const flush = () => { if (rec.state !== 'inactive') rec.stop(); };  // stop() emits the final dataavailable
  document.addEventListener('visibilitychange', () => { if (document.hidden) flush(); });
  addEventListener('pagehide', flush);
  const vt = stream.getVideoTracks()[0];
  vt.addEventListener('ended', flush);
  vt.addEventListener('mute', () => { if (!isPhotoInFlight()) flush(); }); // iOS hidden/interrupted
  return rec;
}
// recovery/assembly: require chunk 0 and contiguous seq; new Blob(chunksSortedBySeq, { type: header.mimeType })
```

## Storage durability — verified by a second pass

- **[H] The IndexedDB spec requires browsers to store values by value. A record keeps its own copy of a Blob or File, so changing or deleting the original afterwards does not affect the record.** Spec section 2.3: user agents 'must support any serializable object', including File and Blob objects. Records 'are stored and retrieved by value rather than by reference; later changes to a value have no effect on the record stored in the database'. Values are the output of StructuredSerializeForStorage. The commit is atomic: 'either all of the changes must be written, or if an error occurs ... the implementation must not write any of the changes'. The iOS Blob bugs listed below are implementation bugs, not spec behavior. Re-checked against the current spec. (https://w3c.github.io/IndexedDB/)
- **[H] Transaction lifetime: a transaction is active only while it is being created and while its own success or error events are being dispatched. Awaiting anything that is not an IDB request (fetch, blob.arrayBuffer(), crypto.subtle.digest, a timer) lets it go inactive. It auto-commits once nothing is pending, and the next request throws TransactionInactiveError.** Spec: a transaction is inactive 'after control returns to the event loop after its creation, and when events are not being dispatched'. The implementation 'must attempt to commit an inactive transaction when all requests placed against the transaction have completed and their returned results handled, no new requests have been placed'. idb README: 'Do not await other things between the start and end of your transaction.' BCD, re-checked: IDBTransaction.commit() is in Chrome 76, Firefox 74 and Safari 15 (Safari iOS mirrors Safari). (https://w3c.github.io/IndexedDB/ ; https://github.com/jakearchibald/idb ; https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/IDBTransaction.json)

**Recommendations**

- Treat on-device storage as a working cache that can still be lost, and make an off-device copy the real guarantee. Track each item's state (captured, verified, exported) and keep showing an 'N items not backed up' badge until it is exported. Nothing in any browser makes data survive the user clearing it, deleting the iOS Home Screen app, losing the phone, Lockdown Mode (IndexedDB disabled), or a change of origin.
- Pin the final origin BEFORE the first real job walk. On <owner>.github.io/<repo>, every other Pages project of that account shares the same IndexedDB, Cache API, quota and persist() grant, and adding a custom domain later strands existing data on the old origin. Prefer a dedicated origin (for example a custom subdomain set up from day one), use a unique database name (for example 'dcr-jobwalk'), and never call caches.keys()-delete-all or localStorage.clear() from any app on that origin.
- iOS: run job walks only from the Home Screen app. Detect it with matchMedia('(display-mode: standalone)') OR matchMedia('(display-mode: fullscreen)') OR navigator.standalone === true, because iOS can report fullscreen instead of standalone (WebKit bug 264218). If none of these is true, block capture and show 'Add to Home Screen' steps. Explain that data from a Safari tab will not appear in the app, and that turning off 'Open as Web App' (iOS 26+) puts it back in a Safari tab with the 7-day wipe.

**Strict, verified IndexedDB write (error name preserved; no awaits inside the tx)**

```js
async function sha256Hex(buf) {
  const d = new Uint8Array(await crypto.subtle.digest('SHA-256', buf));
  return Array.from(d, (b) => b.toString(16).padStart(2, '0')).join('');
}

function txDone(tx) {
  return new Promise((resolve, reject) => {
    let reqErr = null;
    tx.oncomplete = () => resolve();
    // Bubbled request errors arrive here BEFORE the abort; tx.error is still null at this point.
    tx.onerror = (e) => { reqErr ??= e.target.error; };
    // QuotaExceededError (incl. at commit time) is on tx.error here; check err.name.
    tx.onabort = () => reject(tx.error || reqErr || new DOMException('Transaction aborted', 'AbortError'));
  });
}

export async function saveChunkVerified(db, rec /* {key:[id,seq], mime, buf:ArrayBuffer} */) {
  const hash = await sha256Hex(rec.buf); // async work BEFORE the transaction
  const tx = db.transaction('chunks', 'readwrite', { durability: 'strict' }); // Chrome 83+, Safari/iOS 15+
  tx.objectStore('chunks').put({ ...rec, hash });
  await txDone(tx);
  const rtx = db.transaction('chunks', 'readonly');
  const got = await new Promise((res, rej) => {
    const r = rtx.objectStore('chunks').get(rec.key);
    r.onsuccess = () => res(r.result); r.onerror = () => rej(r.error);
  });
  if (!got || got.buf.byteLength !== rec.buf.byteLength || (await sha256Hex(got.buf)) !== hash) {
    throw new Error('verify failed');
  }
}
```

```js
// Build `blob` BEFORE the tap; call within 5 s of the tap (Blink and WebKit activation lifespan).
export async function exportBackup(blob, name) {
  if ('showSaveFilePicker' in window) {            // Chrome desktop 86+, Chrome Android 132+
    try {
      const h = await showSaveFilePicker({ suggestedName: name });
      const w = await h.createWritable(); await w.write(blob); await w.close();
      return 'saved';
    } catch (e) { if (e.name === 'AbortError') return 'cancelled'; throw e; }
  }
  // No picker: in practice iOS Safari. WebKit has no type/size check, so a zip is OK.
  // (Chrome Android canShare() returns true for zip, but share() rejects with NotAllowedError.)
  const file = new File([blob], name, { type: 'application/zip' });
  if (navigator.canShare?.({ files: [file] })) {
    try { await navigator.share({ files: [file] }); return 'shared'; }
    catch (e) {
      if (e.name === 'AbortError') return 'cancelled-or-read-failed'; // WebKit uses AbortError for both
      return 'needs-second-tap'; // NotAllowedError: show a button whose click calls downloadBlob()
    }
  }
  downloadBlob(blob, name);
  return 'downloaded';
}
export function downloadBlob(blob, name) {
  const url = URL.createObjectURL(blob);
  const a = Object.assign(document.createElement('a'), { href: url, download: name });
  document.body.append(a); a.click(); a.remove();
  setTimeout(() => URL.revokeObjectURL(url), 60000);
}
```

**Recommendations**

- Data safety first. Persist every photo as soon as it is captured, together with a plain-object copy of its raw fix: lat, lng, accuracy, altitude, altitudeAccuracy, timestamp, platform, raw magnetic heading, the declination used and the calibration version. Never store GeolocationCoordinates directly: it throws DataCloneError, and toJSON only exists on iOS 18+ and Chrome 126+. Keeping the raw data lets you re-solve calibration or heading later without losing anything.
- Call navigator.storage.persist() after install and after the first saved photo. Both WebKit and Chrome evict a whole origin at once, photos included, and WebKit grants persistence mainly to Home Screen web apps. Keep any tile cache small and capped in its own Cache, because it shares the origin's quota.
- Basemap choice. For a business app, use Esri through a free ArcGIS Location Platform account: the token ibasemaps World_Imagery URL, 2M tiles a month free, 'Powered by Esri' plus the live copyrightText, and a calendar reminder to rotate the key before its at-most-one-year expiry. The token-less legacy endpoint works, but it is not clearly licensed and is in 'mature support'. Google Map Tiles is the alternative, with billing, a browser-exposed key it says should be IP-restricted, 15k tiles a day by default, and no offline use. Pick one provider; don't mix Google with Esri or USGS in one layer switcher.
- Set the real native zoom per site. For Esri, run the tilemap probe; its placeholders come back as HTTP 200 so Leaflet can't detect them. For Google, take the maximum of maxZoomRects at the site. For USGS, use 16. Set maxZoom 22 on the map and the tile layer. Avoid detectRetina: it fetches about 4x the tiles.
- No pre-downloading of job-site tiles with any provider. Use crossOrigin:true so SW entries aren't 7 MB opaque responses. Honor Cache-Control (Esri and USGS send max-age=86400) and ETag, and cap the cache with LRU.
- Leaflet: vendor 1.9.4 with the recomputed SRI hashes. Don't adopt 2.0.0-beta.1, published 2026-11-02. Draw the rotated plan with your own CSS-matrix overlay built from three projected corners; the Rotated plugin was last released in 2019 and only tested on 1.0. Don't use map.distance() (spherical haversine) for calibration math.
- Geolocation: always pass enableHighAccuracy:true and maximumAge:0. Only stop a watch on PERMISSION_DENIED; TIMEOUT and POSITION_UNAVAILABLE do not end it. Hold a Screen Wake Lock during averaging and re-request it on visibilitychange. If accuracy is 2000 m or more, or stays above about 50 m, tell the user to allow Precise location: Chrome's site prompt, Android Settings > Apps > Chrome > Location > precise, or iOS Location Services > Safari Websites > Precise Location.
- On iOS, call getCurrentPosition from a button tap instead of trusting navigator.permissions.query; it reports 'prompt' until the API has been used in that page load. Call DeviceOrientationEvent.requestPermission() from the same kind of tap before relying on the compass.
- Heading: webkitCompassHeading on iOS and deviceorientationabsolute on Android both use magnetic north, while GPS calibration and plan north are true north. Add the site's declination (NOAA WMM; +12.84° in Sacramento, 2026) and store both raw and corrected values. Never use coords.heading for camera direction: it is direction of travel and null when standing still.
- Altitude is raw metadata only. iOS gives orthometric (EGM2008, MSL) height, Android Chrome gives WGS84 ellipsoid height, and the two differ by the geoid undulation (about -30 m in California). Chrome never fills altitudeAccuracy, and iOS may pass an invalid altitude with altitudeAccuracy 0.
- Calibration: average each point for 20-30 s with the screen held on and drop the first third. Spread the points as far apart as the site allows; rotation error ≈ σ/L rad, about 5.7° at L=30 m with σ=3 m. Use 4 or more points when possible. Use a similarity fit, or a rigid fit when a scale bar is known; never a 3-point affine. Show the user an honest expected error of about 3-6 m and several degrees.
- Calibrate from GPS fixes rather than letting the user align the plan by eye over Google imagery. The latter may count as 'creating content based on Google Maps Content' (ToS 3.2.3(c)) — my reading.
- Render PDF plans to at most about 5 MP per canvas on phones (pdf.js's mobile limit is 5,242,880 px), or tile large plans, to avoid blank or crashing canvases on iPhone and Android.

```js
function makeLocal(lat0, lon0) {
  const s = Math.sin(lat0 * D), w = 1 - E2 * s * s;
  const N = A / Math.sqrt(w), M = A * (1 - E2) / (w * Math.sqrt(w));
  const kx = N * Math.cos(lat0 * D) * D, ky = M * D;   // meters per degree
  return { toEN: (lat, lon) => [(lon - lon0) * kx, (lat - lat0) * ky],
           toLL: (e, n) => [lat0 + n / ky, lon0 + e / kx] };
}
```

**2D similarity / rigid fit (Umeyama closed form) + residuals**

```js
// P: plan points in METERS, y UP (flip image y first). Q: GPS points in local [E,N].
// E = a*x - b*y + tx ; N = b*x + a*y + ty ; scale = hypot(a,b), rot = atan2(b,a)
function fitSimilarity(P, Q, fixedScale) {
  const n = P.length; let px=0,py=0,qx=0,qy=0;
  for (let i=0;i<n;i++){px+=P[i][0];py+=P[i][1];qx+=Q[i][0];qy+=Q[i][1];}
  px/=n; py/=n; qx/=n; qy/=n;
  let re=0, im=0, d=0;
  for (let i=0;i<n;i++){ const x=P[i][0]-px, y=P[i][1]-py, u=Q[i][0]-qx, v=Q[i][1]-qy;
    re += x*u + y*v; im += x*v - y*u; d += x*x + y*y; }
  let a = re/d, b = im/d;
  if (fixedScale) { const k = fixedScale / Math.hypot(a,b); a*=k; b*=k; }   // rigid: same angle
  const tx = qx - (a*px - b*py), ty = qy - (b*px + a*py);
  const res = P.map((p,i)=>Math.hypot(a*p[0]-b*p[1]+tx-Q[i][0], b*p[0]+a*p[1]+ty-Q[i][1]));
  return { a, b, tx, ty, scale: Math.hypot(a,b), rotDeg: Math.atan2(b,a)*180/Math.PI, res };
}
// E[sum res^2] = (2n-4)σ² similarity, (2n-3)σ² rigid; σ_rot ≈ σ/sqrt(Σ|p-p̄|²) rad (= σ/L for an equilateral triangle)
```

**Calibration-point averaging (corrected: TIMEOUT does not end the watch; plain-object copy; wake lock)**

```js
async function averageFix(seconds = 30, maxAcc = 20) {
  let lock = null;
  try { lock = await navigator.wakeLock?.request('screen'); } catch {}   // iOS Home Screen: 18.4+
  return new Promise((resolve, reject) => {
    const fixes = []; let lastT = -1;
    const done = (fn, v) => { navigator.geolocation.clearWatch(id); clearTimeout(t); lock?.release().catch(()=>{}); fn(v); };
    const id = navigator.geolocation.watchPosition(p => {
      const c = p.coords;
      if (p.timestamp === lastT || c.accuracy > maxAcc) return; lastT = p.timestamp;
      fixes.push({ lat: c.latitude, lng: c.longitude, acc: c.accuracy, alt: c.altitude,
                   altAcc: c.altitudeAccuracy, t: p.timestamp });   // plain object: coords is not [Serializable]
    }, e => { if (e.code === e.PERMISSION_DENIED) done(reject, e); }, // TIMEOUT/UNAVAILABLE: watch keeps running per spec
    { enableHighAccuracy: true, maximumAge: 0, timeout: 15000 });
    const t = setTimeout(() => {
      if (!fixes.length) return done(reject, new Error('no fix'));
      const keep = fixes.slice(Math.floor(fixes.length / 3));     // drop settling third
      let W=0, la=0, lo=0;
      for (const f of keep) { const w = 1/(f.acc*f.acc); W+=w; la+=w*f.lat; lo+=w*f.lng; }
      done(resolve, { lat: la/W, lng: lo/W, n: keep.length, raw: fixes });   // persist raw for re-solve
    }, seconds * 1000);
  });
}
// If every fix has acc >= 2000 m: the site/app is on Approximate (Chrome prompt, Android app permission, or iOS Precise off).
```
